# 智愿 AI 报考平台参赛改造审查

> 审查基线：2026-08-09 当前 `main` 工作区
> 本文是修改建议，不代表这些能力已经实现。

## 1. 一句话判断

项目已有完整工程骨架和真实业务边界，具备参赛基础；当前最大问题是“亮点分散”。比赛版应从“功能很多的志愿系统”收束为“可解释、可干预、可回放的志愿方案工作流 Agent”。

## 2. 当前能力证据

| 维度 | 当前证据 | 可用作材料的表达 |
| --- | --- | --- |
| 工程 | 122 个后端 Java 文件、19 个 Vue 组件/页面、Docker Compose | 完整 Web 应用，不是静态站点或课件 |
| 数据 | 12 个实体/表，院校、专业、录取线、位次映射、用户、历史、方案、任务、Agent 会话分离 | 业务数据、用户数据和运行轨迹分层建模 |
| 推荐 | 位次/分数差计算、概率分档、冲稳保排序、AI 解释降级 | 大模型不直接决定录取概率 |
| Agent | 9 个白名单工具、会话/消息持久化、参数校验、删除二次确认、本地规则回退 | 受控 Tool Calling，不让模型直接写库 |
| 安全 | Spring Security、JWT、USER/ADMIN、启停与自锁保护 | 权限边界和敏感操作保护 |
| 可靠性 | Redis/RocketMQ 可选、同步回退、错误分类、69 个 `@Test` | 核心链路可测试、可降级 |
| 产品 | 登录、资料、推荐、Agent、历史、方案、管理端路由 | 普通用户与管理员闭环 |

所有数量在定稿前重新运行脚本核验，不要长期硬编码在 PPT。

## 3. P0：参赛前必须处理

### P0-1 资格与原创性确认

现状：仓库当前为公开 GitHub 仓库；往届省赛曾出现“未公开发表或未公开参加过其他比赛”的要求。

动作：

- 将仓库公开状态、首次公开日期、是否参加过其他竞赛写成一页事实说明；
- 把通知原文和仓库链接发给本校承办老师，询问“公开源码是否影响校赛与省赛资格”；
- 获取可留存的书面回复；未确认前不做“肯定符合资格”的陈述；
- 使用 `09_原创性与第三方依赖台账模板.md` 登记所有参考与资源。

验收：有承办方回复；团队成员与贡献排序明确；参考代码与独立实现证据可追溯。

### P0-2 净化源代码与可执行交付包

现状：1783 个已跟踪文件中有 1566 个 `.m2` 依赖缓存文件；仓库和文档含演示密码、开发默认 JWT 值与 Mock token。它们不等同于真实泄漏，但不应直接进入比赛交付包。

动作：

- 源码包排除 `.git`、`.idea`、`.vscode`、`.m2`、`target`、`node_modules`、日志、截图中间件和真实 `.env`；
- 对提交包执行密钥扫描，默认凭据改为比赛现场一次性值或明确的演示环境说明；
- 提供 `SHA256SUMS.txt`、版本号、构建日期、运行环境、离线启动脚本和故障排查；
- 在全新 Windows 环境或虚拟机上按用户手册从零启动一次。

验收：干净机器 15 分钟内可启动；核心演示不依赖公网；压缩包内无真实密钥和本地依赖缓存。

### P0-3 完成一个多步工作流竖切

目标场景：`浙江物理 620 分，偏计算机，不去太远`。

理想闭环：需求补全 → 候选生成 → 硬约束检查 → 冲稳保方案 → 将分数下调 10 分进行 What-if → 显示差异 → 用户确认 → 保存。

必须具备：

- 显式运行状态与步骤；
- 每一步输入、输出、用到的数据来源和规则；
- 可暂停、恢复、修改约束；
- 写入前人工确认；
- 模型不可用时的本地规则降级。

验收：一段 4—5 分钟的现场操作完成全链路；刷新/中断后能恢复；未确认不写入。

### P0-4 建立数据来源与质量证据

动作：

- 每个录取数据集登记来源 URL、年份、省份、科类、采集时间、授权/使用边界和清洗规则；
- 在 UI 和材料中明确“辅助决策，不构成录取保证”；
- 对缺失、冲突、过期数据给出降级提示；
- 禁止用随机 Mock 数据截图冒充真实推荐准确性。

验收：至少选一个省份做完整数据血缘样例；随机抽查 30 条能追溯到原始来源或导入文件。

### P0-5 建立可复跑评测

建议先做 30 条核心离线案例：

- 10 条需求抽取与缺失条件追问；
- 8 条硬约束与冲突处理；
- 6 条 What-if 差异；
- 3 条敏感写操作确认；
- 3 条模型/网络/数据失败降级。

指标只使用能自动或人工复核的定义：字段抽取正确率、硬约束违反数、流程完成率、误写入数、失败降级成功率、P50/P95 时延。

验收：评测输入、预期、实际、通过标准和运行日期完整；失败样例不删除，写明原因。

## 4. P1：显著提升决赛表现

| 建议 | 价值 | 验收方式 |
| --- | --- | --- |
| Trace/证据面板 | 让评委看见“模型选工具、后端计算、规则校验、人工确认”的边界 | 每步展示来源、参数、耗时、状态与错误，不暴露密钥/完整思维链 |
| What-if 对比视图 | 形成强现场效果 | 修改分数/地域/专业偏好后，高亮新增、移除、档位变化及原因 |
| 方案约束检查器 | 把“推荐列表”升级为“可行动方案” | 显示硬约束通过/冲突/待确认，不把软偏好伪装成硬规则 |
| 演示数据快照 | 保证断网可演示 | 固定一份匿名、可追溯数据与预期结果；启动后可一键恢复 |
| 材料事实表 | 避免六份文档互相矛盾 | 版本、数量、接口、表、用例、数据覆盖统一从同一清单取值 |

## 5. P2：有余力再做

- 少量招生简章采用元数据路由 + 全文长上下文，给段落级引用；不默认引入向量数据库。
- 联网搜索仅查学校官网/考试院白名单，保存标题、URL、抓取时间；不得覆盖结构化录取数据。
- 增加方案导出 PDF，但不让排版工作挤占 P0 的工作流和评测。
- 补充可访问性、移动端和性能优化；必须有实际测量再写结果。

## 6. 明确不建议

- 不迁移到多 Agent、LangGraph/Spring AI，只为追热点重写已有 Java 编排。
- 不新增向量库、知识图谱、数字人、语音等难以在截止前验证的范围。
- 不把 RocketMQ、Redis、Docker 数量当创新点；它们只能证明工程完整性。
- 不以“用了大模型”替代算法、数据、评测和安全边界说明。
- 不复制获奖作品或 GitHub 项目的代码、UI、数据、图表、提示词与文案。

## 7. 建议的比赛叙事

### 30 秒版本

智愿 AI 是一个面向高考志愿决策的可解释工作流 Agent。它让大模型负责理解需求和选择受控工具，录取概率仍由可审计的后端规则与数据计算；用户可以修改条件做 What-if 对比，查看每一步依据，并且只有确认后才保存志愿方案。

### 三个核心创新点

1. 决策权分离：模型理解与编排，规则服务计算，人工确认写入。
2. 可干预工作流：中途补约束、修改条件、暂停恢复和对比方案。
3. 可验证证据链：数据来源、规则命中、工具轨迹、评测结果和失败降级可回放。

## 8. 里程碑建议

| 阶段 | 交付 | 停止条件 |
| --- | --- | --- |
| A | 资格确认、数据/依赖台账、干净交付包方案 | 资格或数据授权未确认 |
| B | 单一竖切工作流、状态持久化、人工确认 | 需要改计划外公共接口或表结构 |
| C | What-if、Trace、30 条评测 | 核心闭环仍不稳定 |
| D | 六份说明书、用户手册、PPT、演示视频 | 文档与实际代码不一致 |
| E | 冻结、干净机部署、答辩演练 | 出现阻断问题，仅修阻断 |

具体日期必须以本校最终提交截止时间倒排；往届 8 月 31 日不能直接当作 2026 已确认日期。
