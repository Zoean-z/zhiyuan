## 1. 引言

### 1.1 编写目的

说明本文面向评审专家、开发成员、测试人员和最终用户，定义提交版本的功能边界、质量要求和验收方法。

### 1.2 项目背景

用 200—300 字回答：

- 高考志愿决策中存在什么信息与决策困难；
- 目标用户是谁；
- 为什么普通筛选表或通用聊天模型不足；
- 本作品解决到什么程度，不解决什么。

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| 冲/稳/保 | 基于历史数据与规则生成的风险分档，不构成录取保证 |
| Agent | 选择受控工具并组织多步任务的对话式助手 |
| Tool Calling | 模型只输出受限动作与参数，由后端校验并执行 |
| What-if | 修改一个或多个输入条件后比较方案差异 |
| Trace | 记录步骤、工具、参数摘要、数据/规则来源、状态与耗时的审计轨迹 |

### 1.4 参考资料

列出本届通知、数据来源、需求访谈、原型、仓库版本和第三方标准；每项给出 URL/文件、版本和访问日期。

## 2. 产品概述

### 2.1 产品定位

建议一句话：

> 面向高考志愿场景的可解释、可干预工作流 Agent，大模型负责理解与编排，后端规则负责推荐计算，用户确认后才保存方案。

### 2.2 用户角色

| 角色 | 目标 | 权限边界 |
| --- | --- | --- |
| 普通用户 | 维护画像、查询推荐、与 Agent 协作、保存/回看方案 | 仅访问本人数据 |
| 管理员 | 维护院校、专业、录取线和用户状态 | 不查看密码；不能通过前端绕过权限 |
| 评审/演示用户 | 使用固定演示数据体验闭环 | 不接触真实个人数据或生产密钥 |

### 2.3 运行场景

- 真实后端模式：Spring Boot + MySQL，可选 Redis/RocketMQ/模型 API；
- 离线演示模式：`[说明固定数据与降级能力]`；
- 前端 Mock 模式：仅作界面演示，不能作为真实推荐准确性证据。

### 2.4 范围与非范围

**范围：** 用户/画像、院校/专业推荐、冲稳保解释、对话式工具操作、志愿方案、历史、管理、部署与审计。

**非范围：** 代替考试院正式信息、保证录取、自动提交真实志愿、替用户作最终决定、未经授权抓取或传播个人数据。

## 3. 用户旅程

```text
注册/登录 → 完善省份/科类/分数 → 描述偏好 → 补齐约束
→ 生成候选 → 检查硬约束 → 形成冲稳保方案
→ What-if 对比 → 查看证据 → 人工确认 → 保存与回看
```

标注提交版本中哪些步骤为 `[已实现]`、`[比赛版待实现]`、`[非范围]`。

## 7. 约束与假设

- 历史录取数据只用于辅助判断；政策和计划变化可能导致偏差；
- 模型 API、联网搜索、Redis、RocketMQ 均不得成为核心演示的单点依赖；
- 参赛资格、公开仓库状态和数据授权必须由团队确认；
- 所有演示账号和数据为匿名/虚构，不混入真实考生信息。
