## 3. 写作规则

### 3.1 每个亮点使用四段证据链

1. 问题：用户遇到什么具体困难；
2. 方案：系统做了什么，不先报技术名；
3. 边界：模型、规则、数据和人工分别负责什么；
4. 证据：测试、截图、指标、Trace 或失败样例。

示例：

> 用户用自然语言描述复杂偏好时容易遗漏必要条件。系统先抽取省份、科类、分数和专业偏好，缺项时继续追问；候选由后端规则计算，大模型不直接决定概率；30 条离线案例中 `[待填写实际结果]`。

### 3.2 用词边界

| 不建议 | 建议 |
| --- | --- |
| 精准预测录取 | 基于历史数据与规则给出辅助决策结果 |
| 绝对安全/保证录取 | 保底档/较低风险，并声明存在招生变化 |
| AI 自动填报 | AI 辅助生成草案，用户确认后保存 |
| 自研大模型 | 调用兼容模型 API，自研受控编排与业务工具层 |
| 准确率 99% | 写清数据集、样本数、指标定义和运行日期，否则删除 |
| 完全原创（无说明） | 核心代码原创；依赖、数据、字体、图片和参考逐项列明 |

### 3.3 未实现内容

- 建议项使用“计划/拟实现/后续”，不能放入“系统已实现”。
- 演示模式、真实后端模式和未来路线分别标注。
- `[待核验]` 在提交前必须清零；无法核验就删除对应陈述。

## 4. 截图与图表建议

必须截图：登录/画像、推荐输入、冲稳保结果、Agent 工作流、What-if 对比、Trace/证据、志愿确认、历史回放、管理员数据维护、部署成功。

每张图应包含：图号、场景、输入条件、关键观察点、版本/日期。截图中遮盖 token、密码、真实姓名、个人信息和内部地址。

推荐图表：

- 系统边界图：浏览器、Spring Boot、MySQL、可选 Redis/RocketMQ、模型 API；
- 决策时序图：需求 → 工具 → 规则 → 结果 → 确认；
- 数据血缘图：来源 → 导入 → 清洗 → 表 → 推荐字段；
- What-if 差异图：新增、移除、档位变化；
- 评测矩阵：类别、用例数、通过数、失败原因。

## 5. 10 分钟答辩脚本建议

往届省赛曾采用 10 分钟主讲；本届未确认时，按 8 分钟内容 + 2 分钟缓冲准备。

| 时间 | 内容 | 屏幕 |
| --- | --- | --- |
| 0:00—0:40 | 痛点、目标用户、作品一句话 | 标题 + 用户旅程 |
| 0:40—1:40 | 为什么不是普通聊天机器人 | 决策权分离图 |
| 1:40—5:30 | 完整现场闭环 | 需求补全 → 推荐 → What-if → 确认保存 |
| 5:30—6:30 | Trace、数据来源和安全边界 | 证据面板 |
| 6:30—7:20 | 测试、失败降级、部署 | 评测表 + 离线演示 |
| 7:20—8:00 | 创新点与总结 | 三点结论 |

不要在现场安装依赖、导入大数据、等待公网模型或展示长代码滚屏。

## 6. 高频问题准备

1. 与普通志愿网站的差异是什么？
2. 大模型幻觉会不会影响录取概率？
3. 冲稳保概率如何计算，有没有验证？
4. 数据从哪里来，是否有授权，多久更新？
5. 为什么用 Agent，而不是表单或普通聊天？
6. 断网、模型超时、数据库缺数据怎么办？
7. 如何防止模型越权写入或删除志愿？
8. 参考了哪些开源项目，哪些代码是你们自己写的？
9. 项目是否公开或参加过其他比赛，是否符合资格？
10. 三名成员分别做了什么，如何证明贡献？

每个答案采用“结论一句 + 机制两句 + 证据一句”，控制在 30—45 秒。

## 8. 提交前四轮检查

### 内容检查

- 六份说明书齐全，章节、图表、版本、作者一致；
- 所有 `[待填写]`、`[待核验]`、示例数字清零；
- 文档只写提交版本真实功能。

### 合规检查

- 承办方已确认公开仓库/既往参赛问题；
- 第三方代码、依赖、数据、字体、图标、图片和 AI 辅助情况已登记；
- 无真实个人信息、密钥、Cookie、内部地址和版权不明素材。

### 技术检查

- 干净 Windows 环境从零启动；
- 断网/模型关闭仍可跑核心闭环；
- 自动化测试、构建、演示脚本通过；
- 源码包不含 `.m2`、`node_modules`、IDE 缓存和真实 `.env`。

### 答辩检查

- 8 分钟版、5 分钟压缩版、无网版各演练至少 3 次；
- 主讲人能解释核心算法、数据表、Agent 权限和失败处理；
- 准备本地视频、截图和静态 PDF 作为故障备份。
